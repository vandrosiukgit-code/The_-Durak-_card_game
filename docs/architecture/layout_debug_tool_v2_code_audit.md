# Layout Debug Tool v2: архитектурный аудит кода

Статус: аудит текущей реализации `tools/layout_debug_tool_v2_shell.py`, 2026-05-17.

Основа анализа: [code_quality_principles.md](code_quality_principles.md).

## 1. Вывод

Текущая реализация является рабочим прототипом, который подтвердил основные сценарии v2:
- загрузка layout-данных;
- переключение экранов;
- навигатор объектов;
- hover/select в preview;
- инспектор;
- RAM-сессия;
- `Apply`;
- создание и копирование задач.

Но архитектурно файл `tools/layout_debug_tool_v2_shell.py` уже перерос формат одного shell-файла. Сейчас он совмещает слишком много ответственностей и требует поэтапного разбиения, иначе дальнейшее развитие будет становиться всё более хрупким.

## 2. Что сейчас сделано правильно

1. Есть отдельная v2-утилита, старый `tools/layout_debug_tool.py` не ломается.

2. Shell-интерфейс в основном построен на `pygame_gui`.

3. Ручная отрисовка сосредоточена в `PREVIEW AREA`, что соответствует принятому UI-принципу.

4. Есть явная модель `LayoutObject`, которая защищает часть кода от прямой работы с сырыми `dict`.

5. Есть отдельный `LayoutDataSource`, который уже частично отделяет загрузку `app_config.json` от UI.

6. `Apply` сохраняет layout атомарно и не затирает остальные разделы конфига.

7. RAM-сессия уже существует как пользовательское поведение: изменения не пишутся в файл без `Apply`.

8. Копирование задачи сделано как структурированный текст, а не JSON.

## 3. Главная архитектурная проблема

Класс `LayoutDebugToolV2Shell` стал центром почти всей системы.

Он отвечает за:
- запуск pygame;
- создание окна;
- загрузку layout;
- хранение RAM-сессии;
- выбор экрана;
- выбор объекта;
- построение навигатора;
- построение инспектора;
- построение TO DO;
- обработку pygame-событий;
- обработку `pygame_gui`-событий;
- расчёт preview viewport;
- расчёт hit-test;
- расчёт rect для игровых экранов;
- изменение layout-свойств;
- сохранение `app_config.json`;
- работу с clipboard;
- отрисовку preview.

Это нарушает принцип “один модуль — одна зона ответственности”. Пока файл один, любое новое поведение будет увеличивать риск побочных поломок.

## 4. Конкретные отклонения от принципов

### 4.1. UI владеет бизнес-логикой

Методы shell-класса напрямую меняют layout-данные:
- `_apply_inspector_field_change`;
- `_nudge_selected_object`;
- `_add_task_for_selected_object`;
- `_cancel_selected_object_changes`;
- `_refresh_layout_session_view`.

Проблема:
- сложно тестировать без запуска UI;
- сложно понять, что является источником истины;
- любое изменение UI может сломать модель.

Целевое состояние:
- shell вызывает методы `LayoutSession`;
- `LayoutSession` меняет данные;
- shell только обновляет виджеты.

### 4.2. Persistence смешан с shell

Методы `_atomic_write_config` и `_apply_session_to_config` находятся внутри UI-класса.

Проблема:
- UI знает путь к файлу;
- UI знает формат JSON;
- UI знает детали временного файла.

Целевое состояние:
- отдельный `LayoutConfigRepository`;
- методы `load()` и `save_layout(layout)`;
- UI получает результат операции и показывает статус.

### 4.3. Preview-геометрия зашита в shell

Методы:
- `_game_table_preview_rects`;
- `_main_menu_preview_rects`;
- `_modal_intro_preview_rects`;
- `_modal_endgame_preview_rects`;
- `_layout_rect`.

Проблема:
- shell знает игровые формулы экранов;
- добавление экрана раздувает shell;
- сложно сравнивать preview-геометрию с реальной игровой геометрией.

Целевое состояние:
- отдельный `PreviewGeometryProvider`;
- отдельные адаптеры по экранам;
- shell получает готовый `dict[object_id, pygame.Rect]`.

### 4.4. Событийный обработчик слишком много знает

`handle_event` содержит маршрутизацию всех действий:
- выбор экрана;
- редактирование полей;
- выбор задач;
- apply;
- copy;
- add task;
- clean;
- dismiss/cancel;
- control-кнопки;
- фильтры;
- hitboxes.

Проблема:
- новая кнопка почти гарантированно добавляет новый `if`;
- обработчик становится местом, где легко сломать чужой сценарий.

Целевое состояние:
- слой команд;
- таблица маршрутизации UI-элементов;
- отдельные handlers по зонам: context, inspector, todo, preview.

### 4.5. Геометрия shell задана магическими числами

В файле много `pygame.Rect(...)` с абсолютными координатами.

Проблема:
- любое изменение размера окна требует ручной правки десятков чисел;
- трудно понять, какие числа относятся к layout shell, а какие к игровому canvas;
- высок риск визуального расползания.

Целевое состояние:
- `ShellLayout` или `LayoutMetrics`;
- именованные зоны;
- функции построения rect из базовых размеров;
- константы группируются по зонам.

### 4.6. Есть мёртвые или вводящие в заблуждение элементы

Найдены признаки:
- `self.hover_object` и `self.selected_object` выглядят как старые заглушки и не являются текущим источником истины;
- `_todo_list_html` больше не используется после перехода на `UISelectionList`;
- `edit_task_button` создаётся, но сценарий редактирования задачи не реализован;
- `Copy id` создаётся, но ссылка на кнопку не сохраняется и действие не обработано.

Проблема:
- пользователь видит элементы как рабочие;
- разработчик может принять старое поле за актуальное состояние;
- растёт когнитивный шум.

Целевое состояние:
- удалить неиспользуемое;
- заглушки явно документировать;
- неактивные кнопки скрывать или disabled.

### 4.7. TODO-система смешивает список, выбор и хранение

Методы `_todo_items`, `_selected_todo_item`, `_sync_selected_todo_with_object`, `_todo_selection_items`, `_update_todo_view`, `_add_task_for_selected_object`, `_copy_selected_todo_to_clipboard` находятся в shell.

Проблема:
- TO DO нельзя развивать отдельно;
- редактирование существующей задачи станет сложным;
- clipboard-сценарий смешан с view-сценарием.

Целевое состояние:
- `TodoService`;
- `TodoTask` model;
- `TodoClipboardFormatter`;
- shell только показывает список и вызывает команды.

### 4.8. Нет автоматической проверки инвариантов

Сейчас проверка идёт глазами пользователя.

Минимальные инварианты, которые можно тестировать без GUI:
- загрузка всех supported screens;
- `LayoutObject.from_config_entry` не падает на неполных данных;
- `LayoutSession` меняет только RAM до `Apply`;
- `Cancel` откатывает выбранный объект;
- `Apply` сохраняет layout и не удаляет другие разделы конфига;
- формат `Copy task` не ломает кириллицу.

Проблема:
- дальнейший рефакторинг без тестов будет рискованным.

Целевое состояние:
- сначала выделить чистые классы;
- затем покрыть их небольшими unit-тестами.

## 5. Риски при дальнейшем развитии без рефакторинга

1. Новые функции будут добавляться в один большой класс.

2. Исправление UI может ломать сохранение или TODO.

3. Исправление TODO может ломать выбор объекта.

4. Добавление реального preview игры станет трудным, потому что preview уже связан с shell.

5. Тесты будет трудно написать, потому что логика зависит от pygame-окна.

6. Кнопки-заглушки будут вводить пользователя в заблуждение.

## 6. Целевое разбиение

Предлагаемая структура:

```text
tools/layout_debug_tool_v2_shell.py
  точка входа, создание pygame window, запуск app

durak_app/tools/layout_debug/
  app.py
    сборка зависимостей и главный цикл

  models.py
    LayoutObject
    TodoTask
    SelectionState

  config_repository.py
    загрузка app_config.json
    атомарное сохранение layout

  session.py
    RAM-сессия
    dirty-state
    apply/reset/cancel/dismiss

  preview_geometry.py
    расчёт rect по экранам
    hit-test
    canvas/viewport conversion

  todo.py
    список задач
    создание/редактирование
    форматирование для clipboard

  ui/
    shell_layout.py
      размеры и зоны интерфейса

    context_panel.py
    navigator_panel.py
    inspector_panel.py
    preview_panel.py
    todo_panel.py
    status_bar.py

  commands.py
    команды пользовательских действий
```

Это целевое состояние, не требование сделать всё одним коммитом.

## 7. Приоритеты

### P0 — сначала безопасность данных

- вынести загрузку/сохранение;
- зафиксировать RAM-сессию отдельным классом;
- добавить тесты на сохранение и откат.

### P1 — затем управляемость кода

- вынести модели;
- вынести preview-геометрию;
- вынести TODO-логику.

### P2 — затем UI-разделение

- разделить построение панелей;
- убрать магические числа в `ShellLayout`;
- сделать обработку событий по зонам или командам.

### P3 — затем полировка

- удалить мёртвые поля;
- скрыть/disable неготовые кнопки;
- улучшить дерево навигатора;
- довести `Edit` задачи.

## 8. Решение

Текущий код не нужно “переписывать с нуля”. Его нужно стабилизировать через серию маленьких рефакторингов:

1. Сначала выделить чистые слои без изменения поведения.
2. После каждого этапа запускать утилиту и давать пользователю проверить поведение.
3. Только после этого добавлять новые функции.

Так мы сохраним уже работающую v2 и постепенно уберём архитектурный долг.
