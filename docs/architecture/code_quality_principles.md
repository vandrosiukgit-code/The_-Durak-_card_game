# Принципы качества кода проекта

Статус: базовый архитектурный стандарт, 2026-05-17.

Назначение: дать строгую систему координат для анализа и будущего рефакторинга. Эти принципы важнее вкусовых предпочтений и применяются перед изменением архитектуры кода.

## 1. Один модуль — одна зона ответственности

Модуль должен иметь понятную причину для изменения.

Недопустимо, чтобы один файл одновременно отвечал за:
- загрузку данных;
- модель домена;
- построение UI;
- обработку событий;
- сохранение;
- preview-геометрию;
- clipboard;
- пользовательские сценарии.

Если модуль меняется по многим независимым причинам, его нужно разделять.

## 2. UI не должен владеть бизнес-логикой

`pygame_gui`-элементы должны быть представлением и способом ввода, но не источником истины.

Источник истины:
- layout-модель;
- RAM-сессия;
- выбранный объект;
- выбранная задача;
- статус сохранения.

UI должен только отображать состояние и отправлять команды в слой логики.

## 3. Данные должны проходить через явную модель

Работа с `dict` допустима только на границах системы:
- чтение JSON;
- запись JSON;
- адаптер совместимости с текущим `app_config.json`.

Внутри приложения предпочтительны явные модели и команды:
- `LayoutObject`;
- `LayoutSession`;
- `TodoTask`;
- `ScreenModel`;
- `SelectionState`.

## 4. Сохранение должно быть изолировано

Код записи файла не должен быть размазан по UI.

Отдельный слой persistence отвечает за:
- загрузку `app_config.json`;
- валидацию структуры;
- атомарную запись;
- сохранение остальных разделов конфига;
- сообщения об ошибках.

UI не должен знать деталей временного файла.

## 5. Геометрия preview должна быть адаптером, а не частью shell

Расчёт hitbox/rect для игровых экранов является отдельной ответственностью.

Shell не должен содержать формулы всех игровых экранов внутри себя. Должен быть слой:
- `PreviewGeometryProvider`;
- или набор адаптеров экранов.

Этот слой переводит layout-данные и игровые константы в `pygame.Rect`.

## 6. События должны превращаться в команды

Обработчик событий не должен быть длинной цепочкой `if event`.

События UI должны превращаться в команды:
- `SelectScreen`;
- `SelectObject`;
- `NudgeObject`;
- `ResizeObject`;
- `UpdateProperty`;
- `AddTodoTask`;
- `CopyTodoTask`;
- `ApplySession`;
- `ResetSession`.

Команды проще тестировать, логировать и переносить между UI.

## 7. Временные решения должны быть явно помечены

Если решение временное, оно должно быть отражено в документации и backlog.

Нельзя оставлять временное решение без имени, если оно:
- влияет на архитектуру;
- ограничивает UX;
- усложняет тестирование;
- может сломать данные пользователя.

## 8. Костыль — это не стыдно, если он ограничен

Костыль допустим только если:
- понятно, какую проблему он закрывает;
- есть граница применения;
- есть план удаления;
- он не расползается по коду.

Костыль становится архитектурным долгом, если его начинают использовать как нормальный слой системы.

## 9. Публичное поведение важнее внутренней красоты

Рефакторинг не должен менять пользовательское поведение без отдельного решения.

Перед рефакторингом нужно зафиксировать:
- что уже работает;
- какие сценарии пользователь подтвердил;
- какие ограничения приняты;
- какие тесты или ручные проверки нужны после изменения.

## 10. Маленькие этапы важнее большого переписывания

Рефакторинг должен идти маленькими проверяемыми шагами.

Каждый этап должен:
- иметь понятную цель;
- трогать ограниченную область;
- сохранять рабочий запуск утилиты;
- завершаться ручной проверкой пользователя, если изменение влияет на UI.

## 11. Документация управляет направлением кода

Архитектурная документация фиксирует:
- принципы;
- текущую проблему;
- целевое состояние;
- порядок работ;
- принятые решения.

Код приводится к документации поэтапно. Документация не должна быть задним числом красивым описанием уже случайно получившегося кода.

## 12. Удаление лучше скрытого усложнения

Если функциональность не используется, не реализована или вводит в заблуждение, её нужно:
- удалить;
- скрыть;
- или явно отметить как заглушку.

Особенно это относится к кнопкам, полям и методам, которые выглядят рабочими, но не выполняют действие.
